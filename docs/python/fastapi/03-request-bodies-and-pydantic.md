# Request Bodies & Pydantic

!!! abstract "Learning Objectives"
    By the end of this lesson, you can:

    - Receive JSON data in `POST`, `PUT` and `PATCH` requests using Pydantic models
    - Add rules to fields with `Field()`: lengths, ranges, patterns, defaults, examples
    - Validate emails and write custom validators for business rules from the BRD
    - Model nested data, such as an employee's emergency contact or a list of holidays
    - Read the 422 validation errors that FastAPI returns for bad bodies

**Prerequisites:** [Path & Query Parameters](02-path-and-query-parameters.md), and [Classes & Objects](../oop/01-classes-and-objects.md) from the OOP module.

## Why Request Bodies?

URLs are fine for codes and filters, but adding a new employee or applying for leave involves **structured data**: several fields, sometimes lists and nested objects. That data travels in the **request body** as JSON:

```http
POST /employees HTTP/1.1
Content-Type: application/json

{"first_name": "Kiran", "last_name": "Deshpande", "email": "kiran.deshpande@acme.example", ...}
```

| Method | Body? | Purpose |
|--------|-------|---------|
| `GET` | No | Read |
| `POST` | Yes | Create (or an action, like applying for leave) |
| `PUT` | Yes | Replace |
| `PATCH` | Yes (partial) | Update some fields |
| `DELETE` | Usually no | Remove |

FastAPI reads bodies with **Pydantic**, a library that defines the *shape* of data as a Python class and validates incoming data against it.

!!! example "Real-life analogy: the joining form"
    On a new employee's first day, HR hands them a joining form with boxes and rules: name required, a 10-digit mobile number, date of birth, an emergency contact. HR rejects a form with mistakes before it goes into the system, and points to exactly which box is wrong. A Pydantic model is that form, and FastAPI is the HR executive checking it.

The BRD's rules for these forms will become code in this lesson:

| BRD requirement | Becomes |
|-----------------|---------|
| *"Employee code is generated by the system"* | The client never sends a code; we create one |
| *"Work email must be on the company domain"* | A custom field validator |
| *"Employees must be at least 18 years old on their joining date"* | A model validator comparing two dates |
| *"Each employee has an emergency contact (name, relation, phone)"* | A nested model |
| *"A leave request's end date can't be before its start; half days apply to a single date"* | A model validator on the leave request |

## Your First Pydantic Model

```python title="main.py"
from datetime import date
from enum import Enum
from typing import Annotated, Literal

from fastapi import FastAPI, HTTPException, Path, Query
from pydantic import BaseModel, ConfigDict, EmailStr, Field, field_validator, model_validator

app = FastAPI(title="AcmeHR API")

TODAY = date(2026, 10, 5)   # a fixed "today" so every example gives the same answer (lesson 09 replaces it)

LEAVE_TYPES: list[dict] = [
    {"code": "CL", "name": "Casual leave", "days_per_year": 12, "carry_forward": False, "is_paid": True},
]
EMPLOYEES: list[dict] = [
    {"code": "E-1042", "first_name": "Ananya", "last_name": "Rao", "email": "ananya.rao@acme.example"},
    {"code": "E-1056", "first_name": "Swati", "last_name": "Kulkarni", "email": "swati.kulkarni@acme.example"},
]

EmployeeCode = Annotated[str, Path(pattern=r"^E-\d{4}$")]
INDIAN_MOBILE = r"^[6-9]\d{9}$"


def age_on(born: date, day: date) -> int:
    return day.year - born.year - ((day.month, day.day) < (born.month, born.day))


class LeaveTypeCreate(BaseModel):
    code: str = Field(pattern=r"^[A-Z]{2,5}$", examples=["EL"])
    name: str = Field(min_length=3, max_length=40, examples=["Earned leave"])
    days_per_year: int | None = Field(default=None, ge=1, le=365, description="Empty means no yearly limit")
    carry_forward: bool = False
    is_paid: bool = True


@app.post("/leave-types", status_code=201)
def create_leave_type(leave_type: LeaveTypeCreate):
    new = leave_type.model_dump()
    LEAVE_TYPES.append(new)
    return new


class Location(str, Enum):
    hyderabad = "hyderabad"
    bengaluru = "bengaluru"
    pune = "pune"


class EmergencyContact(BaseModel):
    name: str = Field(min_length=2, max_length=100)
    relation: str = Field(min_length=3, max_length=30, examples=["mother"])
    phone: str = Field(pattern=INDIAN_MOBILE)


class EmployeeCreate(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    first_name: str = Field(min_length=2, max_length=50)
    last_name: str = Field(min_length=1, max_length=50)
    email: EmailStr
    phone: str = Field(pattern=INDIAN_MOBILE)
    gender: Literal["female", "male", "other"]
    date_of_birth: date
    hire_date: date
    department: str
    designation: str
    location: Location
    manager_code: str | None = Field(default=None, pattern=r"^E-\d{4}$")
    emergency_contact: EmergencyContact

    @field_validator("first_name", "last_name")
    @classmethod
    def title_case(cls, value: str) -> str:
        return value.title()

    @field_validator("email")
    @classmethod
    def work_email(cls, value: str) -> str:
        if not value.lower().endswith("@acme.example"):
            raise ValueError("use the @acme.example work email")
        return value.lower()

    @model_validator(mode="after")
    def adult_on_joining(self):
        if age_on(self.date_of_birth, self.hire_date) < 18:
            raise ValueError("employee must be at least 18 years old on the hire date")
        return self


@app.post("/employees", status_code=201)
def create_employee(employee: EmployeeCreate):
    if any(e["email"] == employee.email for e in EMPLOYEES):
        raise HTTPException(status_code=409, detail="An employee with this email already exists")
    last = max(int(e["code"][2:]) for e in EMPLOYEES)
    new = {"code": f"E-{last + 1}", **employee.model_dump()}
    EMPLOYEES.append(new)
    return new


class Holiday(BaseModel):
    holiday_date: date
    name: str = Field(min_length=3, max_length=60)


class HolidayCalendar(BaseModel):
    year: int = Field(ge=2020, le=2100)
    holidays: list[Holiday] = Field(min_length=1)

    @model_validator(mode="after")
    def dates_in_year(self):
        for h in self.holidays:
            if h.holiday_date.year != self.year:
                raise ValueError(f"{h.name} ({h.holiday_date}) is not in {self.year}")
        return self


@app.post("/holidays", status_code=201)
def upload_holidays(calendar: HolidayCalendar):
    return {"year": calendar.year, "count": len(calendar.holidays),
            "first": calendar.holidays[0].name, "last": calendar.holidays[-1].name}


class LeaveType(str, Enum):
    CL = "CL"
    SL = "SL"
    EL = "EL"
    ML = "ML"
    PL = "PL"
    LOP = "LOP"


class LeaveRequestCreate(BaseModel):
    leave_type: LeaveType
    start_date: date
    end_date: date
    duration: Literal["full", "first_half", "second_half"] = "full"
    reason: str = Field(min_length=5, max_length=255)

    @model_validator(mode="after")
    def check_dates(self):
        if self.end_date < self.start_date:
            raise ValueError("end_date can't be before start_date")
        if self.duration != "full" and self.start_date != self.end_date:
            raise ValueError("a half day must start and end on the same date")
        if self.start_date < TODAY and self.leave_type != LeaveType.SL:
            raise ValueError("only sick leave can be applied for past dates")
        return self


@app.post("/employees/{code}/leave-requests", status_code=201)
def apply_leave(
    code: EmployeeCode,
    request: LeaveRequestCreate,
    notify_manager: Annotated[bool, Query()] = True,
):
    employee = next((e for e in EMPLOYEES if e["code"] == code), None)
    if employee is None:
        raise HTTPException(status_code=404, detail=f"Employee {code} not found")
    calendar_days = (request.end_date - request.start_date).days + 1
    return {
        "employee": f'{employee["first_name"]} {employee["last_name"]}',
        **request.model_dump(),
        "calendar_days": calendar_days if request.duration == "full" else 0.5,
        "status": "pending",
        "notify_manager": notify_manager,
    }
```

Let's look at the pieces.

### The model

HR occasionally adds a new kind of leave (Acme added *Paternity leave* last year). A leave type is the simplest model in the file:

```{ .python .no-run }
class LeaveTypeCreate(BaseModel):
    code: str = Field(pattern=r"^[A-Z]{2,5}$", examples=["EL"])
    name: str = Field(min_length=3, max_length=40, examples=["Earned leave"])
    days_per_year: int | None = Field(default=None, ge=1, le=365, description="Empty means no yearly limit")
    carry_forward: bool = False
    is_paid: bool = True
```

- Each **attribute** is a field with a **type**.
- No default means **required** (`code`, `name`). A default makes it **optional** (`days_per_year`, `carry_forward`, `is_paid`).
- `Field(...)` adds rules and documentation, like `Query()` did for query parameters.

When a function argument's type is a Pydantic model, FastAPI reads it from the **body**:

```{ .python .no-run }
@app.post("/leave-types", status_code=201)
def create_leave_type(leave_type: LeaveTypeCreate):
    ...
```

Send one with `curl`: `-X POST` sets the method, `-H` the content type, and `-d` the JSON body:

```bash
curl -s -X POST http://127.0.0.1:8000/leave-types \
  -H "Content-Type: application/json" \
  -d '{"code": "EL", "name": "Earned leave", "days_per_year": "15", "carry_forward": true}'
```

```{ .text .output }
{
  "code": "EL",
  "name": "Earned leave",
  "days_per_year": 15,
  "carry_forward": true,
  "is_paid": true
}
```

Inside the function, `leave_type` is a real Python object: `leave_type.code`, `leave_type.days_per_year`. `leave_type.model_dump()` turns it into a dict. Notice `days_per_year` was sent as the text `"15"` and came back as the number `15`: Pydantic converted it to the declared `int`, and `is_paid` got its default.

Missing optional fields get their defaults. Loss of pay has no yearly limit and isn't paid:

```bash
curl -s -X POST http://127.0.0.1:8000/leave-types \
  -H "Content-Type: application/json" \
  -d '{"code": "LOP", "name": "Loss of pay", "is_paid": false}'
```

```{ .text .output }
{
  "code": "LOP",
  "name": "Loss of pay",
  "days_per_year": null,
  "carry_forward": false,
  "is_paid": false
}
```

!!! tip "Try it in /docs"
    Open `/docs`, expand **POST /leave-types** and click **Try it out**. FastAPI fills in an example body from your model (using `examples=` where you gave them), so you can edit it and execute without writing any curl.

## Validation Errors

Send a body that breaks several rules: a lowercase code, a 400-day allowance, and no name:

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:8000/leave-types \
  -H "Content-Type: application/json" \
  -d '{"code": "wfh", "days_per_year": 400}'
```

```{ .text .output }
{
  "detail": [
    {
      "type": "string_pattern_mismatch",
      "loc": ["body", "code"],
      "msg": "String should match pattern '^[A-Z]{2,5}$'",
      "input": "wfh",
      "ctx": {
        "pattern": "^[A-Z]{2,5}$"
      }
    },
    {
      "type": "missing",
      "loc": ["body", "name"],
      "msg": "Field required",
      "input": {
        "code": "wfh",
        "days_per_year": 400
      }
    },
    {
      "type": "less_than_equal",
      "loc": ["body", "days_per_year"],
      "msg": "Input should be less than or equal to 365",
      "input": 400,
      "ctx": {
        "le": 365
      }
    }
  ]
}
HTTP 422
```

Every problem is listed, with `loc` pointing to the exact field in the `body`. The frontend can show each message next to the right input box.

Wrong types are converted when it's safe (`"15"` becomes `15`) and rejected when it isn't:

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:8000/leave-types \
  -H "Content-Type: application/json" \
  -d '{"code": "BL", "name": "Birthday leave", "days_per_year": "one"}'
```

```{ .text .output }
{
  "detail": [
    {
      "type": "int_parsing",
      "loc": ["body", "days_per_year"],
      "msg": "Input should be a valid integer, unable to parse string as an integer",
      "input": "one"
    }
  ]
}
HTTP 422
```

| `Field()` option | Meaning |
|------------------|---------|
| `default=` | Value when missing (or give `= value` directly) |
| `gt`, `ge`, `lt`, `le` | Number limits |
| `min_length`, `max_length` | String or list length |
| `pattern=` | Regular expression for strings |
| `description`, `examples` | Documentation in `/docs` |
| `alias=` | Accept a different JSON key (e.g. `"firstName"`) |

## Emails, Validators and Strict Models

Adding an employee is HR's most important form, and its model shows more powerful validation:

```{ .python .no-run }
class EmployeeCreate(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    first_name: str = Field(min_length=2, max_length=50)
    email: EmailStr
    phone: str = Field(pattern=INDIAN_MOBILE)
    gender: Literal["female", "male", "other"]
    date_of_birth: date
    location: Location
    ...
```

| Feature | Effect |
|---------|--------|
| `EmailStr` | Must be a valid email address (installed with `fastapi[standard]`) |
| `pattern=r"^[6-9]\d{9}$"` | A 10-digit Indian mobile number starting with 6–9 |
| `Literal["female", "male", "other"]` | Only these exact values; a quick alternative to an `Enum` |
| `extra="forbid"` | Reject unknown fields (catches typos like `"emial"`) |
| `str_strip_whitespace=True` | Trim spaces from every string |
| `date_of_birth: date` | Accepts `"1999-04-12"` and converts it to a `date` object |

Notice what's **not** in the model: the employee code (the system generates it), the `status` (every new hire starts `active`) and the `role` (only an admin may grant one, in a separate step). A model describes what *this* client is allowed to send, not every column in the table.

### Field validators

`@field_validator` runs your own code on a field. Return the (possibly changed) value, or raise `ValueError` to reject it:

```{ .python .no-run }
@field_validator("first_name", "last_name")
@classmethod
def title_case(cls, value: str) -> str:
    return value.title()               # "kiran" -> "Kiran"

@field_validator("email")
@classmethod
def work_email(cls, value: str) -> str:
    if not value.lower().endswith("@acme.example"):
        raise ValueError("use the @acme.example work email")
    return value.lower()
```

The email validator runs **after** `EmailStr` has checked it's a valid address at all, so it only has to deal with the company rule.

### Model validators

`@model_validator(mode="after")` runs after all fields are valid, so it can compare **several** fields. "At least 18 on the hire date" needs both dates:

```{ .python .no-run }
@model_validator(mode="after")
def adult_on_joining(self):
    if age_on(self.date_of_birth, self.hire_date) < 18:
        raise ValueError("employee must be at least 18 years old on the hire date")
    return self
```

!!! realworld "In Real Projects"
    `extra="forbid"` closes a real security hole called **mass assignment**. Look at the `"role": "hr_admin"` in the request above: without the rule, and with code that saved every field it received, anyone filling in a profile form could make themselves an HR admin and read everyone's salary and personal details. Strict input models are a standard defence, and security reviewers check for them.

## Nested Models

Real payloads are nested. You've already sent one: `emergency_contact` is an **object** described by its own model, and its errors point inside it (`["body", "emergency_contact", "phone"]`):

```{ .python .no-run }
class EmergencyContact(BaseModel):
    name: str = Field(min_length=2, max_length=100)
    relation: str = Field(min_length=3, max_length=30, examples=["mother"])
    phone: str = Field(pattern=INDIAN_MOBILE)

class EmployeeCreate(BaseModel):
    ...
    emergency_contact: EmergencyContact
```

A **list** of models works the same way. Every December, HR uploads next year's holiday calendar in one request:

```{ .python .no-run }
class Holiday(BaseModel):
    holiday_date: date
    name: str = Field(min_length=3, max_length=60)

class HolidayCalendar(BaseModel):
    year: int = Field(ge=2020, le=2100)
    holidays: list[Holiday] = Field(min_length=1)
```

```bash
curl -s -X POST http://127.0.0.1:8000/holidays \
  -H "Content-Type: application/json" \
  -d '{"year": 2027, "holidays": [
         {"holiday_date": "2027-01-26", "name": "Republic Day"},
         {"holiday_date": "2027-08-15", "name": "Independence Day"},
         {"holiday_date": "2027-10-02", "name": "Gandhi Jayanti"}]}'
```

```{ .text .output }
{
  "year": 2027,
  "count": 3,
  "first": "Republic Day",
  "last": "Gandhi Jayanti"
}
```

Errors inside a list point to the exact position: `holidays → 1 → holiday_date` means "the second holiday's date":

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:8000/holidays \

         {"holiday_date": "2027-01-26", "name": "Republic Day"},
         {"holiday_date": "2027-02-30", "name": "Founders Day"},
         {"holiday_date": "2027-08-15", "name": "ID"}]}'
```

@model_validator(mode="after")
def check_dates(self):
    if self.end_date < self.start_date:
        raise ValueError("end_date can't be before start_date")
    if self.duration != "full" and self.start_date != self.end_date:

## Common Mistakes

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Missing `Content-Type: application/json` in curl | `422` "Input should be a valid dictionary or object…" | Add `-H "Content-Type: application/json"` |
| Invalid JSON (single quotes, trailing comma) | `422` with `"type": "json_invalid"` | Use double quotes in JSON; validate it |
| An apostrophe inside `-d '...'` (`Sister's`) | The shell ends the string early | Write `'"'"'` for each `'`, or use `/docs` |
| Sending a body with `GET` | Body ignored | Use `POST`/`PUT`/`PATCH` |
| Expecting the model to be a dict | `TypeError: 'EmployeeCreate' object is not subscriptable` | `employee.email`, or `employee.model_dump()` |
| Forgetting `@classmethod` on `@field_validator` | Errors at startup | Put `@classmethod` under `@field_validator` |
| Putting `code`, `status` or `role` in the create model | Clients can set values only the system or an admin should | Leave them out; set them in code |
| Using Pydantic v1 syntax (`@validator`, `.dict()`) | Deprecation warnings / errors | v2: `@field_validator`, `.model_dump()` |

## Interview Questions

!!! interview "1. What is Pydantic and how does FastAPI use it?"
    A data validation library that uses Python type hints to define data models. FastAPI uses Pydantic models to parse and validate request bodies (returning 422 on errors), to serialise and filter responses (`response_model`), and to generate the JSON Schema for the OpenAPI docs.

!!! interview "2. How does FastAPI decide whether a parameter comes from the path, query or body?"
    If the name appears in the path template, it's a path parameter. If its type is a Pydantic model, it's read from the body. Other singular types are query parameters. You can be explicit with `Path()`, `Query()`, `Body()`, `Header()` and `Cookie()`.

!!! interview "3. What is the difference between `field_validator` and `model_validator`?"
    `field_validator` validates or transforms one (or a few) specific fields independently, like checking an email's domain. `model_validator` runs on the whole model (`mode="before"` on the raw input, or `mode="after"` on the validated object) and is used for rules involving several fields, like "end date not before start date" or "18 on the hire date".

!!! interview "4. How do you reject unknown fields in a request body, and why would you?"
    Set `model_config = ConfigDict(extra="forbid")`. It catches client typos and prevents mass-assignment attacks where extra fields like `role` or `salary` are smuggled into the request.

!!! interview "5. What changed between Pydantic v1 and v2 that you'd notice in code?"
    `.dict()` / `.json()` became `.model_dump()` / `.model_dump_json()`; `@validator` / `@root_validator` became `@field_validator` / `@model_validator`; `class Config` became `model_config = ConfigDict(...)`; `orm_mode` became `from_attributes`. v2's core is rewritten in Rust and is much faster.

!!! interview "Scenario: the BRD says 'leave can't overlap an existing approved leave'. Can a Pydantic validator check that?"
    No. A validator only sees the request body, and the overlap rule needs the employee's existing leave from the database. Pydantic handles the *shape* and *self-contained* rules (dates in order, half day on one date); rules that need stored data belong in the endpoint or a service function, which returns a 409 Conflict. You'll build exactly that in lessons 05 and 08.

## Summary

| Concept | Syntax |
|---------|--------|
| Model | `class LeaveTypeCreate(BaseModel): code: str; days_per_year: int \| None = None` |
| Body parameter | `def create(leave_type: LeaveTypeCreate)` |
| Rules | `Field(min_length=2, ge=1, le=365, pattern=..., default=...)` |
| Email | `email: EmailStr` |
| Fixed choices | `Literal["full", "first_half", "second_half"]` or an `Enum` |
| Strict input | `model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)` |
| Custom rule | `@field_validator("field")` + `@classmethod` |
| Cross-field rule | `@model_validator(mode="after")` |
| Nested | `emergency_contact: EmergencyContact`, `holidays: list[Holiday]` |
| Convert | `model.model_dump(exclude={...})` |
| Errors | 422 with `detail[].loc`, `msg`, `input` |
